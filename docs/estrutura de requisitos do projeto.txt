estrutura de requisitos do projeto
introdução do projeto:
O projeto consiste no desenvolvimento de uma aplicação web para gestão de inventário informático. A ideia é criar um sistema onde seja possível registar e organizar computadores de forma simples, agrupando-os em diferentes inventários, que podem representar uma rede, uma sub-rede ou apenas um conjunto lógico de dispositivos. A aplicação vai permitir adicionar equipamentos manualmente, consultar informação relevante como IP, hostname ou estado, e gerir esses dados através de uma interface acessível por browser.

Para além da gestão manual, o sistema também inclui funcionalidades ligadas à área de redes, como a realização de scans para identificar dispositivos ativos dentro de um intervalo de IPs, permitindo depois adicionar esses dispositivos ao inventário. O projeto também prevê autenticação de utilizadores, controlo de acessos e registo de logs, incluindo logs de segurança e RDP. No geral, o objetivo é criar um sistema simples mas funcional, que combine conceitos de desenvolvimento web com algumas funcionalidades práticas relacionadas com redes.

Objetivo mínimo (MVP):
O objetivo mínimo do projeto é desenvolver uma versão funcional do sistema que permita a autenticação de utilizadores, a criação e consulta de inventários, o registo manual de computadores e a consulta básica do inventário através de uma interface web. Para além disso, o sistema deverá incluir uma funcionalidade inicial de scan de rede, capaz de identificar dispositivos ativos num intervalo de endereços IP e apresentar os resultados ao utilizador autorizado.

Requisitos 
O sistema deverá permitir a gestão de inventário informático de forma centralizada, segura e organizada. A aplicação deverá ser disponibilizada através de um web server, comunicar com um web service responsável pela lógica da aplicação e armazenar a informação numa base de dados. O sistema deverá ainda incluir mecanismos de autenticação, autorização e registo de logs, sendo executado em ambiente Docker. Além disso, o sistema deverá permitir a consulta de logs de segurança e logs RDP provenientes dos computadores monitorizados, a descoberta automática de dispositivos na rede através de mecanismos de scan e a disponibilização de uma interface frontend básica para interação com o utilizador. O sistema deverá também permitir a organização de equipamentos em diferentes inventários, associados a sub-redes ou grupos lógicos distintos



Requisitos funcionais 

Convenção de escrita (para revisão e testes)
- Cada RF tem identificador único (RF-XX), ator, pré-condições e critérios de aceitação verificáveis.
- Formato dos critérios: Dado [estado inicial] / Quando [ação] / Então [resultado observável].
- "Referência técnica" aponta para o código atual (frontend + API); serve de rasto para diagramas de sequência UML.
- Um requisito só é considerado cumprido se todos os critérios de aceitação puderem ser reproduzidos manualmente ou via Swagger.


--- Autenticação e sessão ---

RF-01 Iniciar sessão com credenciais válidas
Descrição: O utilizador autentica-se na aplicação e obtém um token de acesso JWT.
Ator: Utilizador registado.
Pré-condições: Existe um utilizador ativo na base de dados; a API está disponível.
Critérios de aceitação:
  CA1: Dado username ou email e palavra-passe corretos, quando submete o formulário de login, então a API responde HTTP 200 com `access_token` e `token_type=bearer`.
  CA2: Dado login com sucesso, quando o frontend processa a resposta, então o token é guardado em `localStorage` e o ecrã principal é apresentado.
  CA3: Dado login com sucesso, então é criado um registo de auditoria com ação `sessao.login` na tabela de logs de sistema.
Referência técnica: `App.handleLogin` → `api.login` → `POST /auth/login` → `auth.login` → `autenticar_utilizador` → `criar_access_token` → `registar_log_sistema`.

RF-02 Rejeitar credenciais inválidas no login
Descrição: Tentativas de autenticação com dados incorretos são recusadas sem expor detalhes do erro.
Ator: Utilizador (ou tentativa não autorizada).
Pré-condições: API disponível.
Critérios de aceitação:
  CA1: Dado identificador ou palavra-passe incorretos, quando é efetuado `POST /auth/login`, então a API responde HTTP 401.
  CA2: Dado resposta 401, quando o frontend apresenta feedback, então o utilizador permanece no ecrã de login e nenhum token é guardado.
Referência técnica: `auth.autenticar_utilizador` (exceção HTTP 401).

RF-03 Consultar identidade da sessão atual
Descrição: O utilizador autenticado obtém os dados da conta e do perfil associado.
Ator: Utilizador autenticado.
Pré-condições: Token JWT válido e não expirado.
Critérios de aceitação:
  CA1: Dado token válido no cabeçalho `Authorization: Bearer`, quando é chamado `GET /auth/me`, então a API responde HTTP 200 com `id`, `username`, `email`, `perfil_id` e `perfil_nome`.
  CA2: Dado token inválido ou expirado, quando é chamado `GET /auth/me`, então a API responde HTTP 401.
Referência técnica: `api.me` → `auth.me` → `deps.get_current_user` → `security.descodificar_access_token`.

RF-04 Carregar dados iniciais após autenticação
Descrição: Após o login, o painel carrega em paralelo as listagens necessárias à navegação.
Ator: Utilizador autenticado.
Pré-condições: Sessão iniciada (RF-01).
Critérios de aceitação:
  CA1: Dado login concluído, quando `App.loadAllData` é executado, então são invocados com sucesso (HTTP 200) os endpoints de inventários, computadores, utilizadores, perfis, localizações, ativos por inventário e histórico do utilizador.
  CA2: Dado carregamento concluído, então o dashboard e as restantes abas dispõem de dados para listagem sem novo login.
Referência técnica: `App.loadAllData` → `api.inventarios.listar`, `api.computadores.listar`, `api.utilizadores.listar`, `api.perfis.listar`, `api.localizacoes.listar`, `api.inventarios.ativosPorInventario`, `api.historicoMeu`.

RF-05 Terminar sessão
Descrição: O utilizador encerra a sessão e o cliente remove o token local.
Ator: Utilizador autenticado.
Pré-condições: Sessão ativa.
Critérios de aceitação:
  CA1: Quando o utilizador termina sessão, então `access_token` é removido de `localStorage` e o estado React de listagens é limpo.
  CA2: Dado sessão terminada, quando tenta aceder a operações protegidas, então é redirecionado para o ecrã de login.
Referência técnica: `App.handleLogout`.


--- Auditoria (histórico de ações do utilizador) ---

RF-06 Consultar histórico pessoal de ações
Descrição: Cada utilizador consulta apenas o seu histórico de eventos registados no sistema.
Ator: Utilizador autenticado.
Pré-condições: Sessão válida; existem ou não registos de histórico.
Critérios de aceitação:
  CA1: Dado utilizador A autenticado, quando chama `GET /auth/me/historico`, então recebe HTTP 200 com lista ordenada por data (máx. 500 entradas) apenas do utilizador A.
  CA2: Dado utilizador sem registos, então a lista devolvida é vazia (`itens: []`) e não provoca erro na interface.
Referência técnica: `auth.historico_do_utilizador` → consulta `LogSistemaDB` filtrada por `utilizador_id`.

RF-07 Registar evento de auditoria a partir do painel
Descrição: Operações relevantes no frontend podem gerar um registo descritivo no histórico do utilizador.
Ator: Utilizador autenticado.
Pré-condições: Sessão válida.
Critérios de aceitação:
  CA1: Dado uma operação concluída com sucesso no painel (`App.withAction`), quando o frontend chama `POST /auth/me/historico`, então a API responde HTTP 201 e o evento fica visível em `GET /auth/me/historico`.
  CA2: Dado falha ao registar histórico, então a operação principal (ex.: criar computador) não é revertida — o registo de auditoria é auxiliar.
Referência técnica: `App.withAction` → `api.registarHistorico` → `auth.registar_evento_historico` → `registar_log_sistema`.


--- Inventários ---

RF-08 Listar inventários acessíveis ao utilizador
Descrição: O sistema apresenta inventários consoante o perfil (admin vê todos; não-admin vê inventários associados).
Ator: Utilizador autenticado.
Pré-condições: Sessão válida.
Critérios de aceitação:
  CA1: Dado utilizador autenticado, quando chama `GET /inventarios/`, então recebe HTTP 200 com lista de inventários incluindo contagens (`total_computadores`, `total_dispositivos_scan`).
  CA2: Dado utilizador não administrador, então a lista não inclui inventários sem associação ao utilizador.
Referência técnica: `inventarios.listar_inventarios` → `_inventarios_visiveis_query` → `deps.is_admin_user`.

RF-09 Criar inventário (administrador)
Descrição: Um administrador regista um novo inventário (tipo normal ou sub-rede).
Ator: Administrador.
Pré-condições: Perfil de administrador; token válido.
Critérios de aceitação:
  CA1: Dado payload válido (`nome`, `tipo_inventario`, `rede` obrigatória se `sub_rede`), quando `POST /inventarios`, então HTTP 201 e o inventário aparece em `GET /inventarios/`.
  CA2: Dado utilizador não administrador, quando tenta `POST /inventarios`, então HTTP 403.
  CA3: Dado inventário `sub_rede` sem rede válida IPv4, então HTTP 422 ou 400 com mensagem de validação.
Referência técnica: `inventarios.criar_inventario` → `require_admin`.

RF-10 Atualizar inventário (administrador)
Descrição: Um administrador altera nome, descrição, tipo ou rede de um inventário existente.
Ator: Administrador.
Pré-condições: Inventário existente; perfil admin.
Critérios de aceitação:
  CA1: Dado `PUT /inventarios/{id}` com dados válidos, então HTTP 200 e os campos alterados persistem na consulta seguinte.
  CA2: Dado ID inexistente, então HTTP 404.
Referência técnica: `inventarios.atualizar_inventario`.

RF-11 Remover inventário (administrador)
Descrição: Um administrador elimina um inventário do sistema.
Ator: Administrador.
Pré-condições: Inventário existente; perfil admin.
Critérios de aceitação:
  CA1: Dado confirmação na interface e `DELETE /inventarios/{id}`, então HTTP 204 e o inventário deixa de aparecer na listagem.
  CA2: Dado ID inexistente, então HTTP 404.
Referência técnica: `inventarios.apagar_inventario` → `App` / `InventariosPage` via `api.inventarios.apagar`.

RF-12 Listar ativos unificados de um inventário
Descrição: Por inventário, o sistema devolve computadores registados e dispositivos descobertos, distinguindo a origem.
Ator: Utilizador autenticado com acesso ao inventário.
Pré-condições: Inventário existente; sessão válida.
Critérios de aceitação:
  CA1: Dado inventário acessível, quando `GET /inventarios/{id}/computadores`, então HTTP 200 com itens que incluem campo `tipo` (`computador` ou `dispositivo_descoberto`).
  CA2: Dado utilizador sem permissão sobre o inventário, então HTTP 403.
Referência técnica: `inventarios.listar_computadores_do_inventario` → `_ativos_unificados_do_inventario` → `_garantir_acesso_inventario`.

RF-13 Pesquisar ativos dentro de um inventário
Descrição: O utilizador filtra ativos de um inventário por termo livre (nome, IP, hostname, etc.).
Ator: Utilizador autenticado com acesso ao inventário.
Pré-condições: Inventário selecionado na interface.
Critérios de aceitação:
  CA1: Dado termo não vazio, quando `GET /inventarios/{id}/computadores/pesquisar?termo=...`, então HTTP 200 apenas com ativos cujos campos pesquisáveis contêm o termo (case-insensitive).
  CA2: Dado termo vazio na interface, então é usada a listagem completa (RF-12) via `api.inventarios.ativos`.
Referência técnica: `inventarios.pesquisar_computadores_do_inventario` → `App.refreshAtivos`.

--- Scan de rede e dispositivos descobertos ---

RF-18 Executar scan de sub-rede num inventário
Descrição: Administrador dispara descoberta de hosts ativos numa rede e persiste/atualiza dispositivos descobertos.
Ator: Administrador.
Pré-condições: Inventário com `tipo_inventario=sub_rede` e rede definida; credenciais de rede fornecidas no pedido.
Critérios de aceitação:
  CA1: Dado pedido válido (`utilizador`, `password`, opcionalmente `rede` e `tipos_log`), quando `POST /inventarios/{id}/scan`, então HTTP 200 com `total_dispositivos_encontrados` e lista `dispositivos_descobertos`.
  CA2: Dado IP novo no inventário, então é criado registo em `dispositivos_descobertos` com `estado=ativo` e `origem_registo=scan`.
  CA3: Dado IP já existente no mesmo inventário, então o registo é atualizado (sem duplicar linha para inventário+IP).
  CA4: Dado IP que existia mas não respondeu no scan atual, então `estado` passa a `inativo`.
  CA5: Dado inventário que não é `sub_rede`, então HTTP 400.
Referência técnica: `inventarios.executar_scan_do_inventario` → `descobrir_dispositivos_enriquecidos` → `obter_dispositivos_descobertos_por_ips` → `coletar_logs_windows` (quando aplicável).

RF-19 Atualizar dispositivo descoberto (administrador)
Descrição: Correção manual de metadados de um dispositivo obtido por scan.
Ator: Administrador.
Pré-condições: Dispositivo existente no inventário.
Critérios de aceitação:
  CA1: Dado `PATCH /inventarios/{inv_id}/dispositivos-descobertos/{disp_id}` válido, então HTTP 200 e campos alterados persistem.
Referência técnica: `inventarios.atualizar_dispositivo_descoberto` → `api.inventarios.atualizarDispositivo`.

RF-20 Remover dispositivo descoberto (administrador)
Descrição: Eliminação de um dispositivo descoberto associado a um inventário.
Ator: Administrador.
Pré-condições: Dispositivo existente.
Critérios de aceitação:
  CA1: Dado `DELETE` bem-sucedido, então HTTP 204 e o dispositivo deixa de aparecer na listagem unificada do inventário.
Referência técnica: `inventarios.apagar_dispositivo_descoberto`.

--- Pesquisa global ---

RF-23 Pesquisa global multi-entidade
Descrição: Pesquisa textual única sobre computadores, inventários, utilizadores e localizações.
Ator: Utilizador autenticado na interface (a API aceita pedido sem token — ver nota de implementação).
Pré-condições: Termo de pesquisa não vazio.
Critérios de aceitação:
  CA1: Dado termo `T`, quando `GET /pesquisar?pesquisa=T`, então HTTP 200 com objeto contendo chaves `computadores`, `inventarios`, `utilizadores`, `localizacoes` (listas, possivelmente vazias).
  CA2: Dado termo vazio ou só espaços, então HTTP 400.

Requisitos Não Funcionais

Desempenho
A API deve responder, em condições normais, em até 2 segundos para operações CRUD comuns (GET, POST, PUT, DELETE).
Listagens com paginação (quando aplicável) devem responder em até 3 segundos para até 1000 registos.
O endpoint de scan deve iniciar processamento em até 2 segundos após o pedido.
O frontend deve apresentar feedback visual de carregamento em operações que demorem mais de 500 ms.

Fiabilidade e Integridade
Operações de escrita devem ser transacionais: em caso de falha, os dados devem manter-se consistentes (rollback).
O sistema não deve permitir criação de registos com campos obrigatórios em falta.
Restrições de unicidade (ex.: número de série, username, email, inventário+IP para dispositivos descobertos) devem ser garantidas pela aplicação e pela base de dados.
Em caso de erro interno, o sistema deve devolver resposta HTTP controlada e não interromper o serviço.
Usabilidade
O sistema deve apresentar uma interface simples e intuitiva para os utilizadores.
O frontend deve permitir navegação clara entre as funcionalidades principais do sistema.

Regras de negócio

Cada computador deve possuir um identificador único.
Cada computador deve possuir um número de série único.
Cada computador deve ter sempre um estado definido.
Apenas utilizadores autenticados podem aceder ao sistema.
Apenas utilizadores autorizados podem criar, editar ou remover computadores.
Apenas administradores podem gerir utilizadores.
Apenas utilizadores autorizados podem executar a funcionalidade de scan de rede.
Todas as ações críticas devem ser registadas em log.
Cada computador pode estar associado a uma localização.
Cada computador pode estar associado a um utilizador responsável.
A remoção de um registo deve ficar refletida nos logs do sistema.
O sistema não deve permitir a criação de registos incompletos nos campos obrigatórios.
Cada log de dispositivo deve estar obrigatoriamente associado a um computador.
O sistema deve permitir a consulta de logs de dispositivo apenas a utilizadores autorizados.
Os logs recolhidos dos computadores devem conservar, no mínimo, a data, o tipo de log e a descrição do evento.
Os logs de dispositivo considerados pelo sistema devem restringir-se a logs de segurança e logs RDP.
Cada utilizador deve poder consultar apenas o seu próprio histórico de ações, salvo utilizadores com perfil de administrador.
Os administradores devem poder consultar os logs de todos os utilizadores do sistema.
Os dispositivos descobertos automaticamente devem poder ser adicionados ao inventário.
Cada dispositivo descoberto deve ser identificado, no mínimo, pelo seu endereço IP.
Os dispositivos devem ter indicação da origem do registo, manual ou automática.
Cada computador deve estar associado a um inventário.
Cada inventário pode agrupar computadores de uma sub-rede ou grupo lógico específico.
Os dispositivos descobertos através de scan podem ser associados a um inventário.
Apenas administradores podem criar, editar e remover inventários.
O scan não deve criar computadores manualmente registados de forma automática.
A identificação de duplicados em dispositivos descobertos deve considerar, no mínimo, inventário + IP.
Quando um dispositivo não for encontrado em scans subsequentes, deve poder ser marcado como inativo mantendo histórico da última vez ativo.
